osu-rotate System Design

A review of how osu-ahr runs an auto host rotation lobby today, and a proposal to rebuild it on .NET 10 as a self-recovering service on your Raspberry Pi, run from a web dashboard.

Summary

osu-ahr has sound game logic and good test coverage of that logic. Its weak points are the parts around the logic: everything lives in memory, it has no real control surface beyond a terminal or Discord, and its only web component is an unauthenticated log viewer.

Recommendation: build one .NET 10 process that holds the bot and a Blazor Server dashboard, in four Clean Architecture projects. A single-writer actor owns the lobby. Pure domain policies decide what happens, and SQLite saves the session before commands are sent, so a restart can rejoin the same room and restore the queue.

The Raspberry Pi 5 has far more capacity than this workload needs. The hard limits come from osu! itself: 10 chat messages per 5 seconds on a personal account, unencrypted IRC, and a lazer API that cannot yet set the host.

What needs you next

Choose a stable hostname for the dashboard, because the osu! OAuth callback needs a fixed URL. Then run the short live tests in Open items before the protocol layer is finalized. One of them decides whether commands you type in-game can reach the bot while it shares your account.

How osu-ahr works today

osu-ahr is a Node.js and TypeScript IRC bot with about 9,000 lines of source, excluding tests and the vendored IRC library. It logs in to Bancho as a normal user, creates a tournament room with !mp make, and manages that room by reading BanchoBot's chat messages and replying with !mp commands.

What happens to a message

  1. irc.js receives a line and emits message. Lobby keeps it only if it targets its own channel.
  2. Lines from BanchoBot go through CommandParser, a set of text matches that yields one of 43 response types. Lines from players are checked for ! and * commands.
  3. Lobby updates its players and host, then emits a typed event.
  4. Each plugin reacts on its own and sends !mp commands back, or asks another plugin to act through a string message.
  5. Outgoing text passes through ChatLimiter at 10 messages per 5 seconds.

The rotation rule

AutoHostSelector keeps a queue with the current host at the front. New players join at the back. The queue rotates when a match starts, and the new front player gets host when the match finishes. Rotating early means a host who leaves mid-match does not disturb the order.

Three edge rules are easy to lose in a rewrite. If a match is aborted before anyone finishes, the same host keeps their turn. If the previous host picked the map and then left, the next host's first start does not rotate again. If someone transfers host by hand, the bot puts it back on the correct player.

Worth keeping

  • The IIrcClient seam and DummyIrcClient, which let the whole bot run without a network. The new Bancho simulator follows the same idea.
  • The test scenarios. The suite has 401 cases: 370 pass, 26 are pending, and 5 fail only because error and description text changed without the tests being updated. The 70 rotation tests are the best specification of the rules.
  • The recovery idea of reading match history to restore order after a restart.

Proposed system

osu-rotate is one process with two faces: a background service that runs the lobby, and a Blazor Server dashboard that observes and commands it. The bot does not depend on anyone having the dashboard open.

One writer owns the lobby

Every input goes into one Channel<LobbyInput>: Bancho events, timers fired through TimeProvider, and dashboard commands. LobbyActor reads them one at a time. This removes locks and race conditions, and a recorded sequence of inputs always produces the same result, which makes the rotation rules directly testable.

Policies are pure: they receive an event and a read-only view of the lobby and return effects. The actor saves the state first, then performs the effects. The dashboard receives immutable snapshots, so a slow browser cannot delay the bot.

Staying within Bancho's limits

OutboundScheduler uses a token bucket of 8 messages per 5 seconds. That leaves 2 of the 10 allowed for you to chat in-game on the same account. Control commands go first, your dashboard messages next, and announcements last. Announcements older than 10 seconds are dropped, and repeat queue announcements merge into one.

Why lazer is an adapter and not the plan

osu!'s referee hub API has structured events for joins, matches and settings. Its page states that the contract is unstable. The documented methods and events include no way to set the host or observe a host change, and chat needs the separate web API. Rotation depends on host control, so LazerTransport stays future work. TransportCapabilities lets the core and dashboard adapt when that changes.

Security

  • Access: OAuth authorization code flow with the identify scope. Only OwnerOsuUserId is authorized, and the check runs on every page and every circuit.
  • Session: HttpOnly, Secure, SameSite=Lax cookie. Data Protection keys persist in /var/lib/osu-rotate/keys so logins survive restarts.
  • Network: Kestrel on loopback, with forwarded headers trusted only from loopback and AllowedHosts set to your hostname. Cloudflare Access can add a second login in front at no code cost.
  • Secrets: the IRC password and OAuth client secret live in a root-owned 0600 file loaded by systemd. Logs never include them.
  • IRC exposure: Bancho offers port 6667 with SSL disabled, so the IRC password crosses the network unencrypted. It is separate from your account password and can be regenerated. Treat it as disposable.
  • Player input: chat is treated as untrusted. Bot commands come from a fixed table, and text from players or map titles is sanitized so it cannot start an !mp command.
  • Service hardening: dedicated user, NoNewPrivileges, ProtectSystem=strict, ProtectHome, and write access only to its data folder.

.NET 10 is an LTS release supported until 14 November 2028, and Microsoft lists Debian 13 on Arm64 as supported. Your Pi has .NET 10.0.11 installed under your home folder, while the current patch is 10.0.15.

Deployment choices

  • Self-contained linux-arm64 publish from your Windows PC. Each deploy brings the latest .NET patches, and the service does not depend on a runtime in your home folder.
  • systemd, not Docker. Docker is available, but a single binary needs no container, and systemd gives restart policy, memory limits and sandboxing directly.
  • Workstation GC with MemoryMax=768M. Native AOT is not an option because Blazor Server does not support it.
  • Install cloudflared, which is currently missing. sqlite3 is optional for manual inspection.
  • Choose a port that does not collide with your existing osb.service. The diagrams assume 5180.

Protecting the microSD card

The only disk is the card, and sudden power loss is the likeliest cause of data loss. SQLite runs in WAL mode, logs go to journald with a size cap, chat is never written to disk, and a nightly VACUUM INTO copy should be stored on another machine. An NVMe HAT or USB SSD is a sensible later upgrade. For a 24/7 IRC connection, Ethernet is preferable to Wi-Fi.

Open items

Needs your decision

  • Dashboard hostname. A named Cloudflare Tunnel needs a domain managed by Cloudflare. Temporary tunnel URLs change, which would break the OAuth callback.
  • History retention. The design keeps matches indefinitely, which the card can hold for many years. Tell me if you would rather expire them.
  • Extra commands. !rank, !update and !mirror are kept by default because they are cheap.
